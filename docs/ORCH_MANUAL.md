# 오케스트레이터 운영 매뉴얼

코드를 직접 읽지 않아도 운영할 수 있도록 쓴 사용 설명서입니다. 저장소마다 같은 엔진(`scripts/orch/` + 워크플로 4개)이 설치되어 있고, 이 문서는 그 공통 사용법입니다.

## 1. 한눈에 보기

| 역할 | 누가 | 하는 일 |
| --- | --- | --- |
| PM | Claude | 요구를 듣고 계획 Issue를 씀, 1시간마다 점검, 판단이 필요할 때만 알림 |
| 구현 | Claude Sonnet / Opus | 스텝 하나씩 구현 (모델은 스텝마다 자동 선택, 7장) |
| 검수 | Codex (기본) → 안 되면 Claude Opus | 스텝 PR을 작성자와 분리된 세션에서 검수 |
| 자동 검사 | GitHub Actions CI | `npm test` 등 |
| 승인 | **사용자** | 시작(`orch:go`), 위험한 변경의 최종 머지 |

흐름: 계획 Issue → `orch:go` → 스텝마다 [구현 → PR → 검수 + CI → 통과면 다음 스텝 / 실패면 수정, 최대 3회] → 최종 PR + 완공 보고서 → 위험 낮으면 자동 머지, 높으면 사용자 승인.

PC를 꺼도 GitHub에서 돌아갑니다. 별도 유료 API는 쓰지 않습니다 (Claude 구독 토큰, Codex 연결).

## 2. 새 작업 시작하기

1. Claude(PM)에게 하고 싶은 일을 말합니다. PM이 계획 Issue를 만듭니다 (템플릿 "Orchestrator 계획").
2. Issue를 보고 괜찮으면 **`orch:go` 라벨**을 붙입니다. 저장소 소유자가 쓴 Issue에 소유자가 붙인 라벨만 동작합니다.

계획은 Issue 본문의 ```` ```json ```` 블록입니다.

| 항목 | 필수 | 뜻 |
| --- | --- | --- |
| `goal` | ✅ | 한 줄 목표 (최종 PR 제목이 됨) |
| `steps[]` | ✅ | 최대 10개. 각 스텝: `id`(1부터), `title`, `task`, `done_when`(기계가 확인할 수 있는 완료 기준) |
| `steps[].stop_if` | | 이런 상황이면 멈추고 사람에게 물어봄 |
| `steps[].model` | | 이 스텝만 모델 지정 (`sonnet` / `opus`) |
| `model` | | 계획 전체 기본 모델 |
| `max_retries` | | 검수 실패 시 수정 횟수 (0~3, 기본 3) |
| `auto_merge` | | `false`면 위험이 낮아도 사람이 머지 |
| `try` | | 완공 보고서의 "확인 방법"에 들어갈 사용법 |
| `context` | | 기술 스택, 제약 등 |

## 3. 진행 상황 보기

계획 Issue 본문 아래의 "진행 상황" 표와 로그 댓글에 모두 기록됩니다. 상황판(모바일)도 같은 정보를 읽습니다.

| 상태 | 뜻 |
| --- | --- |
| 구현 중 | Claude가 스텝을 만드는 중 |
| 검증 중 | 스텝 PR을 Codex(또는 Opus)와 CI가 보는 중 |
| 수정 중 | 검수에서 지적이 나와 Claude가 고치는 중 |
| 최종 확인 중 | 최종 PR의 CI를 기다리는 중 |
| 승인 대기 | 위험한 변경이라 사용자 머지를 기다림 |
| ⏸️ 대기 중 | ON/OFF 스위치나 시간대 때문에 멈춤 (4장). 다시 켜면 자동으로 이어감 |
| 중단 | 사람 판단이 필요함. 사유가 표시됨 (6장) |
| 완료 / 취소 | 끝 |

## 4. 끄고 켜기 (ON/OFF)

GitHub 저장소 **Settings → Secrets and variables → Actions → Variables** 탭에서 바꿉니다. 상황판의 스위치도 같은 값을 바꿉니다.

| 변수 | 값 | 기본(비워두면) | 꺼졌을 때 |
| --- | --- | --- | --- |
| `ORCH_SONNET` | `on` / `off` | on | Sonnet이 할 일을 Opus가 함 (Opus도 꺼지면 대기) |
| `ORCH_OPUS` | `on` / `off` | on | Opus가 할 일을 Sonnet이 함. Codex를 못 쓸 때 대체 검수자가 없어 검수 대기 |
| `ORCH_CODEX` | `on` / `off` | on | Codex를 기다리지 않고 Opus가 바로 검수. Codex가 남긴 결과는 무시 |
| `ORCH_PAUSED` | `on` / `off` | off | `on`이면 새 작업(구현·수정·대체 검수)을 전부 멈춤 |
| `ORCH_WINDOW` | `HH:MM-HH:MM` | 항상 | 한국시간 이 시간대에만 새 작업 시작. 예: `08:00-24:00`, `22:00-06:00`(자정 넘김). 형식이 틀리면 안전하게 "닫힘"으로 처리 |

- **이미 돌고 있는 작업은 끝까지 마칩니다.** 스위치는 새로 시작하는 일만 막습니다.
- 꺼서 멈춘 작업은 Issue에 "⏸️ 대기"로 한 번 기록되고, 시간 초과로 중단되지 않습니다.
- 다시 켜면 **최대 20분 안에**(순찰 주기) 자동으로 이어집니다. 바로 이어가려면 Actions → `orchestrator` → **Run workflow**를 누르면 됩니다.
- 한계: Codex 앱이 PR을 보고 스스로 리뷰하는 것은 GitHub 밖 설정이라 막을 수 없습니다. 꺼져 있을 때는 그 결과를 판정에 쓰지 않을 뿐입니다. 완전히 막으려면 Codex 설정에서 이 저장소의 Code review를 끄세요.

## 5. 승인 — 자동 머지와 확인 필요

- 스텝 PR은 검수 + CI 통과 시 통합 브랜치(`orch/run-N`)에 자동으로 합쳐집니다. 판정한 커밋에서 바뀌었으면 합치지 않습니다.
- 최종 PR(→ `main`)은 **위험이 낮으면 CI 통과 후 자동 머지**, 아래에 해당하면 **완공 보고서와 함께 승인 요청**합니다.
  - DB 구조 변경(마이그레이션·스키마), 로그인·결제·권한·세션·토큰 관련 코드, 인증서
  - GitHub Actions·저장소 설정, 오케스트레이터 자체 변경
  - 배포·빌드 설정(`vercel.json`, `next.config` 등), 환경변수 파일
  - 새 외부 패키지·의존성 잠금 파일 변경, 변경 파일 40개 초과
- 배포는 하지 않습니다. 배포는 사용자가 결정합니다.

## 6. 멈췄을 때

| 하고 싶은 것 | 방법 |
| --- | --- |
| 이어가기 | 원인을 해결한 뒤 계획 Issue에 `orch:go` 라벨 |
| 취소 | `orch:cancel` 라벨 |
| 위험 변경 머지 | 최종 PR의 "주의할 점"을 읽고 Merge |

PM(Claude)이 1시간마다 점검합니다. 일시적인 문제(Actions 오류, 사용량 한도 등)는 스스로 재개하고(같은 run에 최대 2회), 사람 판단이 필요하면 "무슨 일인지 / 선택지 / 추천"을 Issue에 남기고 폰으로 알립니다.

## 7. 구현 모델 선택

1. 스텝의 `model` → 2. 계획의 `model` → 3. 자동
   - 자동: 스텝 제목·내용에 DB·인증·로그인·비밀번호·결제·권한·보안·배포 관련 말이 있으면 **Opus**, 아니면 **Sonnet**
2. Sonnet으로 검수에 **2번** 떨어진 스텝은 다음 수정부터 Opus로 올립니다.
3. ON/OFF 스위치가 마지막에 적용됩니다 (4장).

완공 보고서 "검사 결과" 표에 스텝별 구현 모델·**쓴 스킬과 보조 에이전트**·검수자·수정 횟수가 나옵니다. 스텝 PR 본문의 "도구 사용 (자동 기록)"에는 구현 Claude가 실제로 쓴 도구 횟수, 스킬(예: ECC `verification-loop`), 보조 에이전트(예: `build-error-resolver`), 돌린 검증 명령(typecheck/test/build)이 실행 기록에서 자동으로 뽑혀 남습니다. ECC 효과는 이 기록과 수정 횟수를 run별로 비교해서 봅니다.

## 9. 안전장치 (하지 않는 것)

- 소유자가 아닌 사람의 Issue·라벨로는 시작하지 않습니다.
- 구현하는 Claude는 푸시·PR·워크플로 수정 권한이 없고, `.github/`·`scripts/orch/`를 바꾸면 푸시를 거부합니다.
- 검수는 구현과 다른 세션·계정에서 하며, 정해진 계정이 쓴 판정만 믿습니다.
- 사용자 승인 없이 위험한 변경을 `main`에 넣지 않고, 배포하지 않습니다.

## 10. 모바일 상황판 (ai-orchestrator 앱)

| 탭 | 볼 수 있는 것 |
| --- | --- |
| 프로젝트 | 저장소별 자동 진행 작업 — 상태, 스텝 n/N 통과, 대기·중단 사유, 다음 행동 |
| AI 팀 | **사용량**(Claude 5시간·7일 사용률과 리셋 시각, Codex 한도 소진 여부) + Sonnet / Opus / Codex / 전체 일시정지 스위치, 작업 시간대 (관리자 로그인 시 조작) |
| PM 브리핑 | 사용자가 결정할 것 — 머지 승인 대기, 중단, 스위치 때문에 대기 중인 작업 |

- 상황판 스위치는 4장의 저장소 변수를 바꾸고 엔진을 바로 깨웁니다. 그래서 대기 작업이 20분을 기다리지 않고 이어집니다.
- 상황판이 꺼져 있거나 고장 나도 엔진은 GitHub 변수만 보고 움직입니다.
- 서버 설정(Vercel): `ORCH_REPOS`(보여줄 저장소, 쉼표 구분), `ORCH_GITHUB_TOKEN`(해당 저장소 Issues 읽기, Variables 읽기·쓰기, Actions 읽기·쓰기). 토큰이 없으면 읽기만 됩니다.

### 사용량은 어떻게 재나요
- `usage` 워크플로가 매시 17분에 돌아요. Claude Code를 Haiku로 한 번("OK" 한 단어) 실행하면 Claude가 돌려주는 한도 정보(5시간·7일 사용률, 리셋 시각)가 나오고, 그걸 `orch:usage` 라벨 Issue에 저장해요. 값은 **구독 계정 전체** 기준이라 직접 대화로 쓴 양도 포함돼요. 전체 일시정지 중에는 확인을 건너뛰고 마지막 값을 유지해요.
- Codex는 3시간마다 공식 `codex app-server`의 `account/rateLimits/read`로 5시간·주간 사용률과 리셋 시각을 읽어요. 이때 필요한 Codex 로그인 정보는 암호화해서(AES-256, 열쇠는 시크릿 `CODEX_AUTH_KEY`) GitHub Actions 캐시에 보관해요. 실행할 때마다 복원 → 조회 → 토큰이 바뀌었으면 다시 암호화해서 저장 → 실행 컴퓨터에서 삭제하는 순서로 돌아요. GitHub 리뷰 기록으로 본 "한도 소진" 여부도 같이 표시해요.
- **처음 한 번 (폰으로)**: ① 저장소 Settings → Secrets and variables → Actions → New secret → 이름 `CODEX_AUTH_KEY`, 값은 20자 이상 아무 문자열 ② Actions → `codex-login` → Run workflow ③ 실행 요약(또는 `orch:usage` Issue 댓글)에 나온 주소를 열고 코드를 넣어 승인.
- 로그인이 풀리면 상황판과 `orch:usage` Issue에 "폰 로그인 필요"가 뜨고, ②~③만 다시 하면 돼요. 이 로그인 정보는 사용량 조회에만 쓰여요.
- 문서화되지 않은 정보라 형식이 바뀌면 "확인 불가"로 표시돼요. 엔진 동작에는 영향이 없어요.
